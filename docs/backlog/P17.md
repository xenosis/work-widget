# P17 — 외부 백로그 주간 변화 추적 (이번 주 변경 사항 패널)

## 목적

P14.2(외부 백로그 task 목록 대시보드)에 **주간(월~일) 기준의 변화 추적** 기능을 추가합니다. 사용자의 최종 목표는 "매주 Codex와 함께 실행할 때 위젯에서 자동으로 주간 변화(추가/상태변경/삭제된 작업)를 요약해서 주간보고에 넣을 수 있게 하는 것"인데, P17은 그 1단계입니다. 위젯 자체에서 "이번 주 들어 처음 확인한 시점"의 각 백로그 상태를 자동으로 기준선으로 저장해 뒀다가, 같은 주 안에 다시 확인할 때마다 지금 상태와 비교해서 무엇이 추가/변경/삭제됐는지를 표시합니다.

## 쉬운 설명

P14.2는 등록된 다른 프로젝트의 backlog.json 파일들에서 현재 작업 목록을 읽어와 상태별로 보여줍니다. P17은 그 기능에 **"이번 주 들어 뭐가 바뀌었는가"를 추적하는 기능**을 더합니다.

**구체적으로:**

1. **첫 번째 확인(주당 1회)**:
   - 월요일에 "외부 백로그 현황" 패널을 열면, 각 등록 소스의 현재 작업들이 그 주의 "기준선"으로 자동 저장됩니다.
   - 저장 과정은 사용자가 몰라도 되게 배경에서 조용히 이루어집니다(오류 알림도 표시하지 않음 — 다음 주에 다시 시도).

2. **같은 주 내 재확인**:
   - 화요일~일요일에 같은 패널을 다시 열면, 지금 상태를 월요일 기준선과 비교합니다.
   - **"이번 주 변경 사항"** 섹션에 다음이 표시됩니다:
     ```
     이번 주 변경 사항
     
     + 새로 추가: P2.1 — 예제 작업 (todo)
     ↻ 상태 변경: P2.2 — 진행중에서 완료로 (in_progress → done)
     − 사라짐: P2.3 — 삭제되거나 원본에서 없어짐
     
     (또는 변경이 없으면: "이번 주 변경 사항 없음.")
     ```

3. **주 경계를 넘어갈 때**:
   - 월요일이 되면(getThisWeekRange() 계산으로 자동 감지), 기준선이 자동으로 새로 갱신됩니다.
   - 새로운 주의 "첫 확인" 상태가 새 기준선이 됩니다.

4. **추가 개선 사항**:
   - 상태별 개수를 한 줄로 요약 (예: "총 12개 · todo 3 · done 5 · in_review 1")
   - 이 요약과 변경 사항을 모두 이 패널 상단에 바로 보여줍니다.

5. **한계(문서/UI에 명시)**:
   - 기준선은 "그 주 들어 처음 위젯을 열었을 때"만 설정되므로, 예를 들어 월요일 하루 종일 위젯을 안 켰다면 월요일 상태를 소급 재구성할 수 없습니다.
   - 따라서 이 추적은 "매주 최소 한 번은 위젯을 켜서 확인한다"는 전제에서만 정확합니다.

## 필요한 입력

**기술적 의존성:**
- P14.1, P14.2가 이미 완료돼야 합니다 (백로그 소스 데이터 모델, task 읽기 IPC, task 목록 UI).
- `electron/dataStore.js`에 `backlog_sources` 엔티티의 `weekly_snapshot` 필드가 정의돼 있어야 합니다 (P17에서 추가).
- `src/lib/dateRange.js`의 `getThisWeekRange()` 함수가 존재해야 합니다 (주 시작일 계산 — 기존 함수 재사용).

**컴포넌트 및 훅:**
- P14.2의 `BacklogStatusPanel.jsx` 컴포넌트가 이미 존재해야 합니다.
- P14.1의 `useBacklogSourceRead` 훅이 존재해야 합니다.
- 부모 컴포넌트(Schedule.jsx)가 data 상태와 setData 함수를 가져야 합니다.

## 결과물

### 1. 순수 함수 라이브러리 (`src/lib/backlogWeeklySnapshot.js`)
- `resolveWeeklySnapshot(snapshot, currentTasks)`: 
  - 기준선이 없거나 지난 주 기준이면 현재 tasks를 이번 주 기준선으로 만듭니다.
  - 이미 이번 주 기준선이면 참조를 그대로 반환합니다(불필요한 재저장 방지).
  
- `diffWeeklyChanges(snapshot, currentTasks)`:
  - 기준선과 현재 tasks를 id로 비교해 이번 주 변화를 세 가지로 분류합니다:
    - `added`: 기준선에 없던 id (새로 추가된 작업)
    - `removed`: 기준선에는 있었는데 지금 없는 id (삭제됨)
    - `statusChanged`: 같은 id인데 status가 다른 항목들 (`previousStatus` 필드 포함)
  
- `countTasksByStatus(tasks)`:
  - 상태별 개수 요약을 위한 경량 함수.
  - 입력: task 배열
  - 출력: `[{ status: string, count: number }, ...]` (등장 순서 유지)

### 2. 기준선 저장 핸들러 (`src/screens/Schedule.jsx`의 `handleRotateSnapshot`)
- **리뷰 반영으로 설계가 바뀐 부분**: 처음엔 별도 액션 팩토리(`src/lib/backlogSnapshotActions.js`)로 뺐었지만, 저장 가드를 `ref`로 바꾸는 과정에서 "ref를 다른 함수의 인자로 넘기면 렌더 중 읽을 수도 있다고 오인해 막는" eslint 규칙(`react-hooks/refs`)에 걸려, 다른 일정 CRUD 핸들러 세 개와 같은 방식으로 `Schedule.jsx` 안의 평범한 함수로 합쳤다(그 파일은 삭제됨).
- `handleRotateSnapshot(sourceId, snapshot)`: 백그라운드에서 새 `weekly_snapshot`을 해당 소스에 저장한다. 다른 저장이 진행 중이면(`savingRef.current`) 에러 없이 건너뛰고 `false`를 돌려준다(실제로 시도했으면 `true`) — 이 반환값으로 호출부(`BacklogStatusPanel.jsx`)가 "건너뜀"과 "시도 후 실패"를 구분한다.
- **`savingRef`(useRef)**: `saving`(state)만으로 가드하면 갱신이 다음 렌더에야 반영돼, 소스가 여러 개 등록된 경우 그 기준선 갱신들이 "같은 렌더"에서 함께 가드를 통과할 수 있었다(critical-reviewer가 지적한 High 결함) — 즉시 갱신되는 `ref`로 바꿔 하나씩만 통과시킨다.
- **`dataRef`(useRef)**: `savingRef`만으로는 부족했다 — mutex에 막혀 대기하던 호출이 나중에 통과할 때도 여전히 "자기가 만들어질 때(그 렌더)의" `data` 클로저를 썼다. 두 소스가 동시에 기준선을 새로 만들어야 하는 상황 + 그 사이 일정 추가를 함께 실행하면, 나중에 실행된 호출이 방금 끝난 다른 저장을 옛 데이터로 덮어써 지워버렸다(재검증 도중 자체 발견, 5회 반복 재현으로 확인). 모든 쓰기 핸들러(`handleAddSchedule`/`handleEditSchedule`/`handleDeleteSchedule`/`handleRotateSnapshot`)가 `setData` 호출과 같은 자리에서 `dataRef.current`도 동기적으로 갱신하도록 고쳐 해결했다(`useEffect`로만 동기화하면 커밋 지연 때문에 부족함이 재현됨).

### 3. 데이터 모델 업데이트 (`electron/dataStore.js`)
- `backlog_sources` 엔티티의 필드 추가:
  - `weekly_snapshot`: `null` (기본값) 또는 `{ weekStart: "YYYY-MM-DD", tasks: [...] }`
  - 새로 등록된 소스는 처음엔 `null`이고, 첫 확인 시 자동으로 채워집니다.

### 4. UI 통합 (`src/components/BacklogStatusPanel.jsx`)
- 기존 `SourceTaskGroups` 컴포넌트 확장:
  - `resolveWeeklySnapshot` 호출로 기준선 필요 여부 판단.
  - `diffWeeklyChanges` 호출로 변화 분류.
  - 새 기준선이 필요하면 `useEffect`에서 `onRotateSnapshot` 콜백 실행(렌더 중 상태 조정 규칙 위반 방지).
  - **`attemptedWeekStartRef`(useRef)**: 저장이 계속 실패하는 환경에서는 매 렌더 무제한 재시도가 됐다(critical-reviewer 지적, High) — 같은 `weekStart`는 이 컴포넌트 인스턴스당 "실제로 저장을 시도한 적이 있으면"(`onRotateSnapshot`이 `true`를 돌려준 경우, 성공이든 실패든) 한 번만 시도하도록 기억한다. 다른 소스의 저장과 겹쳐 "건너뛴"(`false`) 경우는 기억하지 않아, 곧 이어지는 재렌더에서 자연스럽게 다시 시도된다. 패널을 접었다 다시 펼치면(재마운트) 이 ref가 초기화돼 같은 주 안에서도 한 번 더 시도할 기회가 생긴다.
  - `useBacklogSourceRead(source.path, getThisWeekRange().weekStart)`: 두 번째 인자(`refreshKey`)를 새로 추가해, 패널을 오래 펼쳐 둔 채 주가 바뀌어도 오래된 상태로 새 기준선을 잘못 만들지 않도록 그 시점에 다시 읽는다(P14.1 당시엔 `path`만으로 충분했음 — critical-reviewer 지적, Medium).
  
- 새로운 UI 섹션:
  - **상태별 요약 줄** (`<p className="backlog-weekly-summary">`):
    - 예: "총 12개 · todo 3 · done 5 · in_review 1"
  
  - **이번 주 변경 사항** (`<div className="backlog-weekly-changes">`):
    - 제목: "이번 주 변경 사항"
    - 추가된 작업: "+ 새로 추가: [title] ([status])"
    - 상태 변경: "↻ 상태 변경: [title] ([previousStatus] → [status])"
    - 삭제된 작업: "− 사라짐: [title]"
    - 변경이 없으면: "이번 주 변경 사항 없음."

### 5. 부모 컴포넌트 통합 (`src/screens/Schedule.jsx`)
- `BacklogStatusPanel`에 new prop 전달:
  - `onRotateSnapshot={handleRotateSnapshot}` (Schedule.jsx 안에 직접 정의된 평범한 함수 — 위 "2." 참고)

### 6. 테스트 스위트 (`src/lib/backlogWeeklySnapshot.test.js`)
- vitest로 작성된 테스트:
  - `resolveWeeklySnapshot`: 기준선 없음/이번 주/지난 주 세 경우
  - `diffWeeklyChanges`: 추가/제거/상태변경/변화 없음/null 기준선 다섯 경우
  - `countTasksByStatus`: 상태별 개수와 빈 목록 두 경우

## 선행 작업

- **P14.1** (deps): 데이터 모델(`backlog_sources`), 파일 선택 IPC, 파서, 관리 UI
- **P14.2** (deps): task 목록 대시보드 UI, `useBacklogSourceRead` 훅, 상태별 그룹화
- **P12.16** (간접): 일정 카테고리 관리 — P14.1과 동시에 추가된 data schema 정규화 패턴을 따르므로 참고

P14.2까지 완료되면 P17은 "읽기 전용 파일을 이미 읽을 수 있고, 작업들을 이미 보여줄 수 있으니 이제 변화만 추적하면 된다"는 상황에서 시작됩니다.

## 수행 순서에서의 위치

**큰 틀에서:**
- P14 (외부 백로그 소스 대시보드) — P14.1 + P14.2 두 작업으로 구성
  - **P14.1** (완료): 데이터 모델, 파일 선택, 읽기 전용 파서, 관리 UI
  - **P14.2** (완료): task 목록 대시보드
  - **P17** (이 작업): 주간 변화 추적

**P17의 위치:**
- P14.2가 완료되면 "task 목록을 보여주는 기능"이 끝났으므로, P17은 그 기능 **위에** "변화 추적"이라는 한 겹을 더하는 것입니다.
- P17이 끝나면 위젯에서 주간 변화를 실시간으로 확인할 수 있게 되고, 향후 "이 변화 데이터를 Codex 보고서에 자동 삽입하기"라는 작업(미정, P18 이상)의 입력이 됩니다.

**작업 흐름:**
```
P14.1 (소스 관리)
  ↓
P14.2 (task 목록 표시)
  ↓
P17 (주간 변화 추적) ← 이 작업
  ↓
(미정) Codex 통합으로 주간보고 자동 생성
```
