# P26 — 주간보고 탭 UI

## 목적

TaskDock 위젯의 최종 사용 흐름을 완성하기 위해, **사이드바에 새로운 탭을 추가해 사용자가 실제로 "버튼을 눌러서 주간보고를 생성하고 보는" 경험**을 만드는 것입니다. P25에서 뒷단(Codex 호출, 에러 처리)이 준비되었으므로, P26은 그 기능을 **사용자가 보고 조작할 수 있는 화면으로 연결**하는 작업입니다. P25/P26 완료로 **"이 주에 우리 프로젝트가 뭐가 바뀌었는지 자동으로 한국어 보고서로 만들어주는 것"** 이라는 사용자의 최종 목표(P17부터 여러 차례 언급)의 핵심 기능이 완성됩니다.

## 쉬운 설명

이 위젯의 최종 목표는 "이 주에 우리 프로젝트가 뭐가 바뀌었는지 자동으로 한국어 보고서로 만들어주는 것"입니다.

**P26의 화면은 이렇게 만들어졌습니다:**

1. **예시 문장 등록 (화면 맨 위)**
   - 큰 입력창(textarea)에 "보고서를 이런 톤으로 써줄 예시"를 한 번만 입력하고 저장
   - 그 다음부턴 모든 프로젝트의 보고서가 이 톤을 따름
   - 다만 현재는 예시 문장이 비워 있어, 실제 회사의 문체에 맞는 예시를 나중에 채워야 함(사람이 입력)

2. **등록된 백로그 소스별로 생성 버튼**
   - 각 프로젝트(소스) 한 줄씩 표시
   - "생성" 버튼 → 로딩 표시("생성 중...") → 결과 문단이 화면에 나타남
   - 결과 옆에 "복사" 버튼으로 클립보드에 복사 가능
   - 마지막 생성 시각도 함께 표시
   - 생성을 다시 누르면 이전 결과를 새 결과로 덮어씀

3. **실패했을 때**
   - Codex(AI 도구)가 설치 안 됐거나, 인증되지 않았거나, 시간이 걸려서 못 기다렸을 때
   - 각 경우마다 다른 이해하기 쉬운 안내 문구("Codex를 설치하세요", "먼저 로그인해주세요" 등)를 보여줌
   - Codex 원문 에러 메시지도 함께 표시(기술자가 상세히 확인 필요할 때)
   - 앱이 죽지 않고 계속 다른 탭을 이용할 수 있음

## 필요한 입력

### 기술적 의존성
- **P25 완료**: Electron IPC를 통해 `window.api.generateWeeklyReport()` 함수 사용 가능
- **P17 완료**: 이번 주 변경 사항을 감지하는 함수들(`resolveWeeklySnapshot`, `diffWeeklyChanges`) 사용 가능
- **P14.1, P14.2 완료**: 등록된 백로그 소스(backlog_sources) 데이터 모델과 파일 읽기 IPC 준비

### 데이터 구조
- `data.json` 구조:
  - `weekly_report_example`: 문자열(전역 예시 문장, 기본값 `''` — 회사 실제 문체는 아직 사용자가 채워야 함)
  - `backlog_sources[]` 배열의 각 항목에 `weekly_report` 필드 (nullable, `{weekStart, text, generated_at}` 형태)

## 결과물

### 1. 신규 파일: `src/screens/WeeklyReport.jsx`

주간보고 탭의 전체 화면을 담당합니다. 주요 기능:

- **전역 예시 문장 영역**
  - textarea + 저장 버튼
  - 저장하면 `data.json`의 `weekly_report_example` 필드에 반영
  - 변경사항은 자동 저장(다른 소스의 저장과 겹치지 않도록 프라미스 체인으로 직렬화)

- **등록된 소스 목록**
  - `backlog_sources` 배열의 각 항목마다 `WeeklyReportSourceRow` 컴포넌트 1개씩 배치
  - 소스가 없으면 "백로그 소스를 먼저 등록하세요" 안내

- **데이터 일관성 보호 (critical-reviewer 지적 반영)**
  - Codex 생성은 최대 90초가 걸릴 수 있어, 그동안 사용자가 다른 탭으로 이동하면 이 화면이 언마운트될 수 있음
  - 언마운트 후에도 저장 체인이 계속 실행되는데, "탭을 떠난 시점"의 오래된 데이터로 전체 `data.json`을 덮어쓰면 그 사이 다른 탭(할일 추가, 메모 변경 등)에서 생긴 변경이 조용히 사라질 수 있었음
  - **수정 후**: 저장 직전에 항상 디스크의 최신 상태(`window.api.loadData()`)를 다시 읽어서, 그 위에만 주간보고 결과를 적용 → 언마운트 여부와 무관하게 항상 안전

### 2. 신규 파일: `src/components/WeeklyReportSourceRow.jsx`

등록된 백로그 소스 하나를 다루는 행(row) 컴포넌트입니다.

- **"생성" 버튼**
  - 클릭 → P25의 IPC `window.api.generateWeeklyReport()` 호출
  - payload: `{ sourceLabel, exampleSentence, weekData }`
    - `weekData`는 이 순간의 백로그 변경 사항(added, statusChanged, removed)을 계산해 전달
    
- **최신 데이터 보장 (critical-reviewer 지적 반영)**
  - 소스 행이 마운트될 때(또는 주가 바뀔 때)만 읽던 task 목록을 그대로 사용하면, 위젯을 트레이에 며칠 띄워둔 채 "생성"을 누를 때 오래된 상태로 "이번 주 변화"를 계산해 실제 변화가 빠진 보고서가 조용히 만들어질 수 있었음
  - **수정 후**: 생성 직전에 항상 한 번 더 실제 파일을 다시 읽어서(`window.api.readBacklogSourceTasks(source.path)`) task 목록을 갱신한 뒤 주간 변화를 계산 → 며칠 후에 생성해도 항상 최신 상태 반영

- **로딩 표시**
  - 생성 중이면 "생성 중..."이라는 텍스트와 스피너 표시
  - 버튼은 비활성화(disabled)

- **결과 표시**
  - IPC 성공 시, 생성된 보고 문단 + 마지막 생성 시각 + 복사 버튼
  - 복사 버튼 클릭 → 문단 전체가 클립보드에 복사됨
  - 다시 "생성"을 누르면 (같은 주라면) 이전 결과를 새 결과로 덮어씀

- **에러 표시**
  - IPC 실패 시 code(`NOT_INSTALLED`, `AUTH_ERROR`, `TIMEOUT` 등)에 따라 다른 안내 문구 표시
  - 사용자 친화적 메시지 + codex 원문 에러 메시지 함께 표시
  - 버튼은 다시 활성화되어 재시도 가능
  - **실제 성공 경로 검증 (critical-reviewer 지적 반영)**
    - 초기 구현은 Codex 미설치 에러와 재시도만 테스트했는데, 실제 성공 경로(codex가 성공적으로 텍스트를 반환)와 재실행 시 결과 덮어쓰기를 확인한 적이 없었음
    - **수정 후**: 스텁 codex 실행 파일을 만들어(실제 API 비용 없이 표준입력을 그대로 돌려줌) 전체 IPC/프로세스 실행 경로를 왕복시켜, UI로 예시 문장을 두 번 다르게 저장하고 각각 생성했을 때 결과 텍스트가 그 예시 문장을 반영하고, 저장된 결과가 실제로 교체되는 것까지 확인 → 이 과정에서 Windows cmd.exe 부수 버그도 발견 및 수정(명령 이름 자체가 따옴표로 감싸지면 배치 파일의 자기 자신 경로 확장이 깨짐)

### 3. 신규 파일: `src/lib/weeklyReportActions.js` + 테스트

`data.json`에 실제로 쓸 내용을 계산하는 순수 함수들입니다 (부수 효과 없음).

#### `buildExampleSaveData(data, exampleText)`
- 전체 `data` 객체를 그대로 펼치되(spread) `weekly_report_example` 필드만 새 값으로 교체
- 입력: 현재 전체 data 객체, 새 예시 문장 문자열
- 출력: `{ ...data, weekly_report_example: exampleText }`(다른 필드는 그대로 보존)

#### `buildReportSaveData(data, sourceId, report)`
- 전체 `data` 객체를 그대로 펼치되, `backlog_sources` 배열 중 `id`가 일치하는 항목 하나만
  `weekly_report: report`로 교체(다른 소스는 그대로 보존). 일치하는 id가 없으면 배열이 그대로
  돌아온다(사람이 소스를 지운 직후 등 드문 경합에도 안전).
- 입력: 현재 전체 data 객체, 대상 소스 id, 이미 구성된 report 객체(`{weekStart, text, generated_at}`
  — 이 세 필드를 만드는 것은 `WeeklyReportSourceRow.jsx`의 몫이고, 이 함수 자체는 "어디에
  끼워 넣을지"만 담당)
- 출력: `{ ...data, backlog_sources: nextSources }`

**테스트 (vitest 3개)**:
- `buildExampleSaveData`가 `weekly_report_example`만 바꾸고 나머지 필드는 그대로 두는지
- `buildReportSaveData`가 일치하는 id의 소스만 바꾸고 다른 소스는 그대로 두는지
- `buildReportSaveData`에 일치하는 id가 없으면 아무 소스도 안 바뀌는지

## 확인 필요

### 1. 회사 실제 예시 문장 입력 시점
현재 `weekly_report_example` 필드는 기본값이 빈 문자열(`''`)로 비어 있습니다. 실제 회사의 문체에 맞는 예시 문장을 언제 채울 것인지 확인 필요합니다.

**현재 상태**: UI에서 사용자가 직접 textarea에 입력해 저장 가능하도록 준비됨 — 실제 입력은 운영 시점의 사람 결정.

### 2. "인증 안 됨" 분류의 완벽성
P25의 알려진 한계: 현재 구현에서는 codex stderr의 영문 키워드 매칭(`unauthorized`, `authenticate`, `not logged in`, `401` 등)으로 `AUTH_ERROR`를 판정합니다. 로케일/버전마다 문구가 달라질 수 있으므로 완벽한 분류가 아닙니다.

**이 화면에서의 영향**: 해당 에러 코드를 그대로 표시하므로, P25의 키워드 분류 정확도가 곧 이 화면의 사용자 경험에 영향을 줍니다.

**확인 방법**: 실제 다양한 Codex 버전/환경에서 인증 실패 메시지 수집 및 P25의 키워드 확장 필요.

### 3. 외부 백로그의 프롬프트 인젝션 위험
P25의 알려진 한계: 생성 과정에서 외부 백로그 소스의 `title`/`owner` 텍스트가 사용자의 명시적 승인 없이 Codex 프롬프트에 그대로 들어갑니다. 이론상 프롬프트 인젝션 위험이 있습니다(근본 차단은 안 하고 방어 문구만 추가됨).

**이 화면의 설계 대응**: 생성된 텍스트를 자동으로 전송하지 않고, 사람이 직접 **확인한 뒤 복사 버튼으로만** 클립보드에 담게 설계했습니다(사용자 review flow 보장). 따라서 의도하지 않은 프롬프트 인젝션 내용이 외부로 나가는 것을 사용자 단계에서 차단합니다.

**확인 방법**: 생성된 텍스트를 사용자가 항상 먼저 눈으로 확인하고 필요시 수정 후 사용하도록 운영.
