# P6.3 — data.json 스키마 검증/마이그레이션 유틸

## 목적
data.json의 최상위 구조(projects/todos/memos/schedules 4개 배열 키)가 손상되어도 앱이 안정적으로 동작하도록 한다. 손상된 파일은 백업하고, 부분 저장 시도(예: 일부 배열만 저장)를 거부해서 의도하지 않은 데이터 손실을 방지한다.

## 쉬운 설명
JSON 파일이 깨졌거나 필요한 배열 키가 없으면, 그 파일을 `<filename>.corrupt-<timestamp>`로 백업한 후 기본 구조로 다시 로드한다. 또한 렌더러가 실수로 일부 배열만 저장하려고 하면(예: `{memos: [...]}` 만) 그걸 거부해서 나머지 데이터가 영구 삭제되는 사고를 방지한다.

## 필요한 입력
- B3 최상위 스키마: projects/todos/memos/schedules 4개 배열이 필수
- data.json이 존재할 수도, 없을 수도 있음 (없으면 새로 생성)

## 결과물
`electron/dataStore.js`의 다음 기능들:
- `normalizeData()`: 최상위 구조 검증 (loadData에서 관용적으로 사용)
- `backupCorruptFile()`: 손상 파일을 타임스탬프와 함께 백업
- `saveData()`: 저장 전 4개 배열 키가 전부 있는지 확인 (없으면 예외)
- 임시 파일(`tmp+rename` 방식)로 원자적 쓰기 구현
- 두 번 로드해도 배열 참조가 공유되지 않도록 각각 독립 복제

## 선행 작업
P0.3 — dataStore.js의 기본 loadData/saveData

## 수행 순서에서의 위치
P6.3은 최상위 구조 손상만 담당한다. 개별 레코드의 누락 필드(예: todo.tags가 없음)는 P6.4에서 따로 처리한다. 두 작업은 보완 관계: P6.3이 "4개 배열이 존재하는가", P6.4가 "각 배열의 레코드가 필수 필드를 갖는가"를 담당한다.

## done_when을 확인하는 방법
1. `npm test`에서 dataStore 테스트가 통과하는지 확인
2. 손상된 JSON 파일을 심어 테스트:
   - 파싱 실패 JSON → 원본이 `.corrupt-<timestamp>`로 백업됨
   - 키 누락(예: `{todos: [...], memos: [...]}` — projects/schedules 없음) → 자동 보정 후 기본값 채움
3. 부분 저장 시뮬레이션:
   - `saveData({memos: [...]})` (다른 3개 배열 없음) → 예외 던짐, 파일 변경 안 함
4. 원자성 확인:
   - saveData 후 `.tmp-*` 임시 파일이 디스크에 남지 않음
5. 참조 안전성:
   - 같은 데이터를 두 번 로드해도 배열이 같은 인스턴스를 가리키지 않음
