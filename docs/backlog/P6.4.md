# P6.4 — data.json 레코드 단위 필드 기본값/마이그레이션

## 목적
P6.3이 최상위 구조(4개 배열의 존재성)를 담당하면, P6.4는 각 레코드의 필드 단위 손상을 방어한다. 구버전 data.json에서 로드한 레코드가 신규 필드를 갖지 않으면 기본값으로 채워서, 최신 화면들이 undefined로 인한 크래시 없이 동작하도록 한다.

## 쉬운 설명
과거 버전에서 저장한 할일(todo)이 priority 필드를 갖지 않으면, 최신 코드에서 `todo.priority.rank`에 접근할 때 TypeError가 난다. P6.4는 loadData 시 이런 누락 필드를 기본값(priority: null 등)으로 자동 채워서 앱이 안전하게 렌더링되도록 한다. 단, 이미 값이 있지만 타입이 잘못된 경우(예: title이 객체, is_recurring이 문자열)는 이 작업 범위에 포함하지 않으며, 각 화면의 기존 방어 패턴에 위임한다.

## 필요한 입력
- P6.3 완료: 최상위 구조 검증 함수
- B3 스키마: 각 엔티티(project/todo/memo/schedule)의 모든 필드 및 기본값 정의

## 결과물
`electron/dataStore.js`의 다음 확장:
- `FIELD_DEFAULTS`: 엔티티별 필드 기본값 맵
- `applyFieldDefaults()`: 개별 레코드에 기본값 적용
- `normalizeData()` 확장: 각 배열의 모든 레코드에 applyFieldDefaults 적용
- `electron/dataStore.test.js` 확장: 5개 이상 테스트 추가 (todo/memo/schedule/project의 누락 필드 채우기 확인 + 기존 값 보존 확인)

## 선행 작업
P6.3 — 최상위 구조 검증

## 수행 순서에서의 위치
P6은 데이터 계층 방어를 단계적으로 강화한다. P6.3이 "4개 배열이 있는가"를 묻고, P6.4가 "각 레코드가 필요한 필드를 갖는가"를 묻는다. 이 둘이 모두 완료되면, 이후 P1~P5의 화면들은 나머지 타입 불일치(P6.6)나 논리 오류 방어만 신경쓰면 된다.

## done_when을 확인하는 방법
1. 구버전 레코드 시뮬레이션: 신규 필드를 갖지 않는 projects/todos/memos/schedules 레코드 4종을 data.json에 직접 심기 (예: todo에서 tags/priority 제거)
2. `npm run dev` 또는 npm 테스트 실행
3. 앱이 예외 없이 기동되고 모든 화면(대시보드/프로젝트/할일전체/메모/일정)이 정상 렌더링
4. 할일 체크박스를 눌러 실제 저장 경로를 거쳐 data.json에 기본값이 반영되었는지 확인
5. `npm test`의 dataStore 테스트들이 모두 통과 (null 보존, 배열 참조 독립, 스키마 밖 필드 보존 등 8개 이상 케이스)
6. `npm run lint`, `npm run build` 통과
